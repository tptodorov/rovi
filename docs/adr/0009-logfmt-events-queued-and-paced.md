# Car events are logged as logfmt lines, queued and paced

The sim car and the board must produce one log that one parser reads, and logging must not disturb the 10 ms control tick. Decided: events are `ev=<name> key=value ... at_ms=<n>` text lines with integers only ([`docs/LOGGING.md`](../LOGGING.md)). Emitters copy a plain record into a ring and a single task formats and writes it, paced to the UART's transmit time. Rejected: `defmt` (the host needs the firmware ELF to decode it, so the sim and the board would need different tooling), JSONL (heavier to format on the S3 with no gain for flat events), and printing in place (`esp-println` locks per fragment and spins when the UART FIFO is full, which stalls the single task that runs every adapter). Cost: one more task, and a log that can drop events under a burst, which it reports as `ev=dropped`.

**Revisit when** the bench shows control-tick jitter from the log task, or tracing at 20 Hz or more (per-setpoint, latency) hits the cap of about 190 lines/s at 115200. Then move the wire format to `defmt` (`esp-println` `defmt-espflash`, decoded by `espflash monitor --elf ... --log-format`), decoded back to the same `ev=` lines on the host so `sim/carlog.py` and the scenarios stay as they are. The costs to accept then: every bench capture must be kept with its ELF, and the sim car needs its own text emitter. RTT over the native USB port is the other option once it is shown to work on this board.
